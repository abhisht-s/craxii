# `getrandom` dependency decision

- Package or tool: `getrandom` from crates.io.
- Dependency kind: Direct normal Cargo dependency.
- Owning subsystem: Stage 9 offline device credential generation.
- Responsible maintainer or owner role: Repository or project owner.
- Primitive supplied: Fill exactly 32 bytes with operating-system cryptographically secure random
  data for one new bearer credential.
- Why the standard library or current approved dependencies are insufficient: The Rust standard
  library exposes no OS CSPRNG fill API. UUID generation is approved for identifier construction,
  not as a bearer-secret API, and a UUID has insufficient/structured token material for this
  contract.
- Permitted layer or scope: Production bearer-token generation only. The dependency may fill one
  exact `[u8; 32]`; it must not generate IDs, nonces for other protocols, randomized retries, or a
  fallback entropy source. Domain/application command types receive only the private secret wrapper
  or its SHA-256 digest.
- Alternatives considered: `rand`, direct OS syscalls, UUID token material, timestamp/process
  entropy, and operator-only token import. `rand` adds unused distribution/RNG abstractions; direct
  syscalls duplicate portability/unsafe work; the next two are not secure tokens; import would make
  secret transport the primary provisioning path.
- Maintenance and security posture: `0.4.3` is already locked through `uuid 1.26.0`, declares MSRV
  `1.85.0`, and builds under the repository Rust `1.98.0`. Updates remain deliberate lockfile,
  upstream-change, platform, advisory, license, and unsafe-surface reviews.
- Exact license evidence: Cargo package metadata declares `MIT OR Apache-2.0`; the packaged crate
  includes both license texts, and the repository cargo-deny policy accepts both without exception.
- Advisory result: The locked advisory gate reports no advisory for `getrandom 0.4.3`; the deny
  ignore list remains empty.
- Feature choice and intended API: Default features are disabled and no feature is enabled. Craxii
  calls only `getrandom::fill(&mut [u8; 32])` and treats any error as a safe provisioning failure;
  there is no pseudo-random fallback.
- Actual graph impact: No new lock package is expected. The active native subtree remains
  `getrandom 0.4.3 -> cfg-if 1.0.4, libc 0.2.189`; target-only lock resolution already owned through
  UUID remains unchanged.
- Build-script, native, and system implications: The crate uses a Rust-only build script for cfg
  detection and invokes no native compiler. It uses platform entropy APIs through target-specific
  Rust/FFI and needs no separately installed native library.
- Unsafe and platform implications: The crate contains reviewed target-specific unsafe FFI,
  syscall/intrinsic, and initialized-buffer operations. On supported native platforms it obtains
  entropy from the OS (`getentropy` on macOS and `getrandom`/documented OS fallback on Linux).
  Craxii adds no unsafe wrapper and never claims deterministic availability on an unsupported OS.
- Secrets, parsing, and persistence implications: Generated bytes immediately become private
  lowercase-hex bearer text. Only SHA-256 of the exact text is persisted. No generated secret is
  logged, serialized, hashed into a client command, placed in an environment, or recoverable from
  storage.
- Removal or migration cost: Low at the generation boundary if a replacement provides the same
  exact OS-CSPRNG fill/failure contract. Existing bearer text and persisted hashes do not change.
- Approved version requirement: Compatible `0.4` line with default features disabled and no
  additional features.
- Resolved and tested version: `0.4.3` from crates.io.
- Review date: 2026-08-28.
- Approval status and approver role: Approved by the repository/project owner through the explicit
  Stage 9 implementation direction on 2026-08-28. Codex recorded the decision and is not the
  approver.
