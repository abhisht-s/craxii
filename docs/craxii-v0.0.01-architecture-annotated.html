Plain-English working glossary

This glossary does not replace the precise definitions later in the document. It gives the reader a reliable first mental model.

Craxii principal
The durable identity of the coworker—the “same employee”—not a model, process, VM, or client.
Conversation
The continuous user-facing relationship surface. It is not the unit the scheduler executes.
Message
A committed piece of conversation, such as one user instruction or one final assistant answer.
Work item
The durable internal job ticket created for an accepted user message.
Canonical
The record whose meaning is authoritative. Copies can move, but migrations must preserve its truth.
Journal
The append-only black box of historical domain facts. Old facts are corrected with new facts, not rewritten.
Projection
A current operational view—like a status board—kept consistent with the journal for fast decisions.
Idempotency
The property that retransmitting the same identified command returns the same logical result instead of doing it twice.
Causation
The durable “because of” link: this event happened because of that earlier command, attempt, or event.
Correlation
The durable case number connecting all activity belonging to one responsibility.
Context manifest
The exact packing list for the evidence rendered into one model invocation.
Provider adapter
The translator and boundary for one inference vendor's authentication, API, native features, errors, and streaming.
Ordered output items
A response represented in the order it arrived—text, tool calls, structured data, refusals, and native items—rather than flattened into one string.
Tool execution intent
The durable job card written before Craxii attempts an external side effect.
Outcome unknown
An honest terminal classification: the side effect may have occurred, but Craxii lacks enough evidence to claim success or failure.
Workstation
Craxii's replaceable computer/body exposed through stable machine primitives.
Artifact
Large evidence bytes—such as logs—with a stable ID, cryptographic hash, provenance, and storage location.
Replay cursor
A durable event offset the client uses to request everything committed after the last item it applied.
WAL
SQLite's write-ahead log: committed changes are recorded before being folded into the main database file.
cgroup/process group
The Linux containment identity used to stop and clean up a command's descendant processes as one owned unit.
Trust domain
The area in which compromise can reach the other assets. In V0, the whole VM is deliberately one such area.
Regenerable
State that can be recreated from authoritative sources, such as a build cache or rendered context.

This document is the normative architecture for implementing Craxii V0.0.01. It is not a tutorial, product pitch, or survey of alternatives. It defines what the version must prove, where every important responsibility lives, which state is authoritative, how commands and side effects are ordered, how failures are represented, and which seams must survive later extraction of Craxii's durable core from its first workstation.

The separate credential and identity architecture remains the long-term direction for authority and identity. Where that mature design asks for external control-plane services or project isolation that V0.0.01 explicitly defers, this document governs the V0 implementation.

Product definition

Major-section guide · plain-English companion

Plain-English significance: Craxii is the durable coworker surrounding model calls, not the model call itself. The relationship, evidence, work, tools, and recovery belong to Craxii even when the inference provider changes. This prevents the product from becoming a chat transcript attached to one vendor. It makes continuity and agency properties of the harness.

Real-life example: A senior engineer is still the same colleague after changing laptops or consulting a different specialist. Likewise, Craxii can ask OpenAI today and another model later without handing its identity to either specialist.

Craxii is one persistent, high-agency AI coworker. It should feel like one continuing relationship:

User <-> Craxii

The user gives responsibilities, not orchestration instructions. Craxii decides how to investigate, call inference, inspect its computer, invoke tools, persist evidence, recover, and report completion or a genuine blocker.

The model is not Craxii. A frontier model is a replaceable inference engine selected for one invocation. Craxii is the durable system around inference:

  • persistent identity;
  • durable history and work state;
  • context construction;
  • model selection and provider adaptation;
  • explicit agent-loop control;
  • tools and process execution;
  • a persistent workstation;
  • recovery and interruption semantics;
  • authority and privilege decisions;
  • artifacts and provenance;
  • client delivery and reconnect semantics;
  • observability and evaluation evidence;
  • later memory, background work, and external authority.

The mature product should preserve one coherent user-facing identity across days, devices, projects, model changes, process restarts, and eventually complete workstation replacement. The V0.0.01 architecture must point toward that product without pretending to implement it.

The workstation is Craxii's computer and replaceable body. Craxii is allowed to administer it broadly. Durable identity roots, catastrophic external authority, recovery roots, and mature canonical state will eventually live outside that body.

Craxii may own its workstation without the workstation owning Craxii.

V0.0.01 end goal

Major-section guide · plain-English companion

Plain-English significance: The first release proves a narrow vertical slice: accept real work, use a real Linux machine, retain honest evidence, restart, and continue. A vertical slice reveals integration failures that isolated prototypes hide while avoiding premature memory, fleet, or distributed-control systems.

Real-life example: It is like proving a new workshop by accepting one real repair, using the actual tools, recording the job, surviving a power cycle, and answering the customer's follow-up—not by drawing ten future workshops.

V0.0.01 has one end goal:

Prove Craxii is a real persistent, tool-using agent runtime: it can receive work, act on its Ubuntu machine, persist what happened, restart, and continue from durable state.

This version is successful only when the real native client, real Rust backend, real provider adapter, real Ubuntu machine, real SQLite journal, and real tool execution path work together. A command-line mock alone is not the release benchmark, though deterministic fakes are required during implementation.

V0.0.01 proves four architectural claims:

  1. Conversation can be a continuous product surface while work_item is the durable execution unit.
  2. Model calls and tool side effects can be surrounded by honest durable intent and outcome records.
  3. A local Linux workstation can be accessed through a replaceable machine boundary rather than leaked throughout the agent runtime.
  4. A native client can disconnect and reconnect without becoming a source of truth or duplicating work.

It does not prove mature memory, production safety, arbitrary in-flight resumption, or workstation-independent identity.

Scope

Major-section guide · plain-English companion

Plain-English significance: Scope lists what engineering must deliver for this version. Anything listed here participates in the definition of done even if its implementation is small. A precise boundary keeps reliability work from being dropped as 'polish' and keeps attractive future features from delaying the core proof.

Real-life example: For a first restaurant opening, the menu might contain one complete meal plus ordering, payment, and cleanup. A larger menu is out of scope, but food safety is not.

V0.0.01 includes:

  • one persistent Craxii principal;
  • one primary user-facing conversation;
  • durable user and assistant messages;
  • exactly one work item for each newly accepted conversational user message;
  • a durable first-in, first-out queue per conversation;
  • at most one active work item per conversation;
  • a Rust backend using Tokio;
  • Axum HTTP and WebSocket endpoints with selected Tower middleware;
  • Serde/JSON boundaries;
  • SQLx with SQLite in write-ahead logging mode;
  • an append-only domain journal and transactionally consistent current-state tables;
  • an explicit agent loop owned by Craxii;
  • naive full-history context with exact causal eligibility and explicit limit failure;
  • a small model-target and provider-adapter layer;
  • one configured OpenAI Responses API target;
  • ordered, provider-independent model output items;
  • a Tool Registry and Tool Execution Service;
  • read_file and run_shell model-facing tools;
  • a small Workstation interface and LocalWorkstation implementation;
  • real Ubuntu filesystem and foreground process execution;
  • user-level and administrative execution modes;
  • bounded output, timeouts, cancellation, process-tree cleanup, and structured failures;
  • idempotent HTTP commands;
  • a replayable durable event cursor;
  • WebSocket delivery of durable events and ephemeral streaming drafts;
  • startup inspection and deterministic classification of incomplete work;
  • one native macOS client using Swift and SwiftUI, with AppKit where required;
  • one x86-64 Ubuntu 24.04 LTS EC2 workstation;
  • encrypted EBS, off-guest snapshots, and systemd supervision;
  • structured tracing and enough usage data to drive V0.0.02.

Non-goals

Major-section guide · plain-English companion

Plain-English significance: Non-goals are deliberate omissions, not forgotten requirements. They define which future problems V0 may expose through seams without solving now. This protects the implementation from speculative frameworks and makes reviews reject accidental scope growth.

V0.0.01 deliberately does not include:

  • context compaction or summarization;
  • vector retrieval, embeddings, or a vector database;
  • full-text search beyond ordinary SQL queries needed by V0;
  • scheduled, webhook-triggered, or autonomous background responsibilities;
  • steering or merging new input into running work;
  • more than one concurrently active work item per conversation;
  • multi-agent orchestration, subagents, worker fleets, or distributed scheduling;
  • automatic recovery inside an arbitrary provider stream or shell execution;
  • automatic retry of ambiguous tool side effects;
  • durable interactive terminals or generic daemon supervision;
  • browser automation or browser isolation;
  • database, cloud, GitHub, or external Model Context Protocol tool integrations;
  • multiple real model providers or sophisticated routing;
  • provider-owned conversation state as a correctness dependency;
  • an external identity, memory, journal, artifact, or Authority Service;
  • workstation-independent canonical state;
  • production credentials, customer data, or production mutation authority;
  • trust realms, project VMs, sandboxes, or multi-tenant isolation;
  • policy compilation for natural-language constraints such as “do not deploy”;
  • iOS, Android, or Windows clients;
  • consumer authentication, teams, billing, or admin consoles;
  • PostgreSQL, Redis, S3, Kafka, Kubernetes, Temporal, or an event bus;
  • LangChain, LangGraph, or any framework that owns the agent loop.

Deferring these is part of the design. An implementation that introduces them to make V0 “more complete” has expanded scope and requires prior architecture approval.

Machine-inspection benchmark

Subsection guide · plain-English companion

Plain-English significance: The machine-inspection benchmark turns one architecture claim into repeatable external behavior. Benchmarks stop teams from declaring success based on an attractive happy-path transcript.

Real-life example: It is a certification run for machine-inspection benchmark: use the actual client, service, state, and machine, then inspect the durable evidence.

The canonical task is:

Inspect your machine and tell me what OS, CPU architecture, current directory, and Git version you have.

The benchmark passes only if all of the following occur:

  1. The native macOS client submits the message through the authenticated HTTP command endpoint.
  2. The command carries a stable client message ID used for idempotency.
  3. One transaction commits the user message, one trigger relationship, one queued work item, the corresponding journal events, and the idempotency response mapping.
  4. The scheduler claims that work item without claiming any other work for the conversation.
  5. Model selection chooses the configured OpenAI target before final context rendering.
  6. A context manifest identifies every source item rendered for the invocation.
  7. A model-invocation intent record commits before the outbound provider request begins.
  8. The provider returns one or more ordered output items containing valid tool calls.
  9. Tool-call arguments are complete, validated, and associated with the selected work item and workspace by Craxii.
  10. A tool-execution intent commits before local execution begins.
  11. The command runs on the Ubuntu workstation, not on the Mac and not inside the model provider.
  12. Captured stdout, stderr, exit status, timing, privilege, path, and cleanup state are persisted after observation.
  13. The tool outcome is rendered into a subsequent model invocation.
  14. A final assistant message and work.completed transition commit atomically.
  15. The client receives durable committed events and may receive ephemeral draft deltas.
  16. The displayed answer matches the observed machine facts.

The model is free to choose one or several calls. The benchmark asserts the orchestration and evidence path, not one hard-coded command sequence.

The failure benchmark has two required paths:

  • A backend death after a non-idempotent tool intent has been recorded but before a terminal result has committed produces tool_execution.state = outcome_unknown and work_item.state = interrupted on recovery. The system does not invent success and does not automatically repeat the command.

Two submissions with the same device ID, idempotency key, command type, and request material produce:

  • one committed user message;
  • one work item;
  • one pair of acceptance/queue events;
  • the original response on every safe retry;
  • a deduplication metric but no second domain event.

Using the same idempotency key with different request material returns a conflict and creates no new domain state.

Architectural invariants

Major-section guide · plain-English companion

Plain-English significance: Invariants are rules that remain true across every path, including retries, cancellation, and process death. Most durable-agent corruption happens when a rare path violates a rule that the happy path assumes.

Real-life example: A bank keeps 'a transfer is never posted twice' true whether the app is fast, slow, disconnected, or restarted. Craxii needs equivalent rules for messages, work, model attempts, and tool side effects.

The following invariants take precedence over implementation convenience.

Identity and ownership

Subsection guide · plain-English companion

Plain-English significance: Identity and ownership gives a stable name or ordering rule to something that must outlive one process or machine observation. Durable identity prevents hostnames, timestamps, provider IDs, or UI positions from accidentally becoming product identity.

Real-life example: An employee number survives office moves and laptop replacements. A desk label or current room number does not, so it cannot serve as the person's identity.

  • craxii_id identifies Craxii. A conversation ID, model-provider ID, process ID, EC2 instance ID, disk ID, socket, and client device ID do not.
  • The backend owns canonical work state and the agent loop.
  • The client owns presentation and local user-interface state only.
  • The model proposes content and tool calls. It owns neither identity, authority, persistence, scheduling, nor execution.
  • The workstation performs machine operations. It does not own conversation, model, journal, or scheduling semantics.

Durability

Subsection guide · plain-English companion

Plain-English significance: Durability isolates one implementation contract so contributors do not have to infer it from neighboring components. Small explicit contracts prevent local convenience from changing identity, causality, recovery, or protocol semantics elsewhere in the system.

Real-life example: During a real signup investigation, the rule named 'Durability' tells the engineer exactly who owns this step, what evidence remains, and what another component may safely assume afterward.

  • SQLite plus committed local evidence artifacts contains canonical V0 control state.
  • Process memory, WebSocket connections, Tokio tasks, provider sessions, and client caches are never canonical.
  • The journal is append-only and authoritative for ordered domain transitions.
  • Mutable tables are current-state and query projections plus detailed attempt records.
  • A domain transition and every current-state mutation it implies MUST commit in one SQLite transaction.
  • A client-visible durable event MUST NOT be published before its transaction commits.
  • A context window is a rendered view and MUST be reproducible from identified source records.

  • Persist the observed terminal outcome after the side effect.

Work and causality

Subsection guide · plain-English companion

Plain-English significance: Work and causality isolates one implementation contract so contributors do not have to infer it from neighboring components. Small explicit contracts prevent local convenience from changing identity, causality, recovery, or protocol semantics elsewhere in the system.

Real-life example: During a real signup investigation, the rule named 'Work and causality' tells the engineer exactly who owns this step, what evidence remains, and what another component may safely assume afterward.

  • Every newly accepted conversational user message creates exactly one work item in the same transaction.
  • A retransmission resolves to the already-created work item.

Model behavior

Subsection guide · plain-English companion

Plain-English significance: Model behavior defines one part of consulting a replaceable inference engine without making that engine Craxii. Selection, canonical intent, provider-native translation, ordered outputs, usage, and retry evidence need distinct owners.

Real-life example: A lead engineer hires a specialist, gives them a tailored brief, preserves their native diagrams and requests, records the fee, and—not the specialist—decides whether the overall job is finished.

  • Model selection precedes model-specific context rendering.
  • OpenAI wire types do not cross the OpenAI adapter boundary.
  • Provider output is an ordered list, not a FinalText | ToolCalls union.
  • Provider-native continuation data may improve a same-provider loop but is never the only copy of durable history.
  • Partial streamed tool arguments are never executed.
  • The agent runtime, not the provider's stop field alone, determines terminality.

Protocol

Subsection guide · plain-English companion

Plain-English significance: Protocol defines a client/server delivery rule that remains correct when connections duplicate, lag, or disappear. The client is a window, so commands and durable events must survive independently of socket lifetime.

Real-life example: Registered mail establishes the instruction and receipt; a live phone call supplies progress. If the call drops, the instruction remains filed and missed updates can be replayed from the last receipt number.

  • Authoritative mutations use idempotent HTTP commands.
  • WebSocket is a delivery channel, not the command or continuity substrate.
  • Durable delivery has a monotonically increasing replay cursor unrelated to wall-clock time.
  • Ephemeral drafts may be lost; committed messages may not.
  • A reconnecting client discards stale drafts and converges on committed state.

Architecture Challenge: TLS termination was unspecified

Major-section guide · plain-English companion

Plain-English significance: This challenge makes HTTPS ownership explicit by putting a small reverse proxy in front of the loopback-only Rust server. Certificate renewal, WebSocket upgrades, and public exposure must have an owner; leaving them implicit creates insecure deployment improvisation.

Real-life example: Caddy is the locked reception desk. It checks the secure entrance and passes visitors to the internal office; it does not decide what work Craxii should do.

Agreed direction: Client transport is HTTPS plus WebSocket Secure, but the prior architecture did not identify the component terminating TLS.

Chosen V0 addition: Use Caddy as a small systemd-managed reverse proxy in front of a loopback-only Axum listener. Caddy owns certificate acquisition/renewal, TLS policy, request forwarding, and WebSocket upgrade forwarding. It owns no Craxii authentication, commands, state, or business logic.

Rationale: Direct TLS in the Rust process couples certificate lifecycle to the application and adds low-value protocol code. An Application Load Balancer adds more AWS infrastructure and cost than a single-user V0 needs. Caddy is a conventional, replaceable edge component.

Tradeoffs: It adds one process and one configuration file. A proxy failure makes the client unavailable while the backend may remain healthy. Proxy logs must omit authorization headers and bodies.

Migration: A later load balancer, private network gateway, or native Rust TLS listener can replace Caddy without changing the Craxii protocol because the backend receives ordinary authenticated HTTP/WebSocket traffic.

V0 blocking status: Resolved by this document. If implementation selects a different terminator, that substitution requires an explicit architecture note and equivalent semantics.

Architecture Challenge: separate data volume

Major-section guide · plain-English companion

Plain-English significance: This challenge separates the OS boot disk from the EBS volume holding Craxii's database, artifacts, and workspace data. A distinct data volume makes replacement, snapshot policy, restoration, and accidental OS rebuilds less entangled with canonical state.

Real-life example: It is the difference between storing company records inside a disposable laptop chassis and keeping them in a removable encrypted records cabinet attached to that laptop.

Agreed direction: Canonical V0 state and workspaces live on encrypted EBS attached to the one EC2 workstation.

Chosen V0 refinement: Keep operating-system state and Craxii data on separate encrypted EBS volumes when provisioning the shared EC2 environment.

Rationale: Reattaching or restoring a data volume is simpler than recovering state intermingled with a failed root filesystem. It makes state classification visible and reduces migration friction without creating a second service or trust boundary.

Tradeoffs: Provisioning and mount configuration gain one additional resource. Root on the VM can still corrupt both mounted volumes. Cross-volume snapshots are not automatically application-consistent.

Migration: The data paths and stable IDs remain the same when the durable core later moves off-machine. Artifact and state repository interfaces, not the volume, are the lasting seam.

V0 blocking status: Not blocking. A one-volume prototype may precede EC2 deployment, but the benchmark deployment SHOULD use the split.

Every spawned Tokio task MUST have an owner and shutdown path.

  • Connection tasks are owned by the Axum server lifecycle.
  • Per-work agent tasks are owned by a scheduler JoinSet or equivalent task collection.
  • Provider stream readers are owned by one model invocation and cancelled with it.
  • stdout/stderr drain tasks are owned by one tool execution and joined before terminal persistence.

The scheduler repeatedly:

  1. Queries conversations with queued work and no active work.
  2. Begins a short write transaction.
  3. Selects the smallest queued ordinal for one conversation.
  4. Guardedly updates that row from queued to running, sets the current runtime_instance_id, and records started_at.
  5. Appends work.started in the same transaction.
  6. Commits.
  7. Spawns the owned agent-loop task in the scheduler's task collection.

  • Cancelling active work atomically transitions it to cancel_requested; asynchronous cleanup follows.
  • Cancelling terminal work returns its existing terminal state as an idempotent no-op.
  • Reusing a cancellation idempotency key with different target material is a conflict.

Transaction boundaries

Major-section guide · plain-English companion

Plain-English significance: Transaction boundaries define which facts must commit together so no observer sees half of a domain decision. Atomicity is how duplicate submission, queueing, side-effect intent, and final answers remain coherent after crashes.

Real-life example: When a bank accepts a transfer, the debit, credit, and receipt reference commit as one unit. Craxii similarly accepts a message, creates work, and records events together.

Command acceptance transaction

Subsection guide · plain-English companion

Plain-English significance: Command acceptance transaction groups database changes that must become visible together or not at all. A crash between related writes must not leave a message without work, an outcome without an attempt, or completion without an answer.

Real-life example: A hotel booking commits the room reservation and confirmation number as one operation; issuing only one half would mislead either the guest or the hotel.

One message command transaction performs this exact logical order:

  1. Look up (device_id, idempotency_key).
  2. If present, compare command type and request hash and return the stored response or conflict.
  3. Lock/update the conversation row and allocate conversation_work_ordinal using next_work_ordinal.
  4. Pre-generate message, work, event, and correlation IDs.
  5. Insert the user message.
  6. Allocate conversation stream sequence and append message.accepted.
  7. Insert work_items(state='queued').
  8. Insert work_item_inputs(relationship='trigger') referencing the acceptance event.
  9. Allocate work stream sequence and append work.queued caused by message.accepted.
  10. Increment conversations.next_work_ordinal and projection version.
  11. Construct the exact success response including the last journal offset.
  12. Insert the client_commands row containing that response.
  13. Commit.
  14. Notify scheduler and live event delivery as hints.

No client can observe a committed message without its work item or vice versa.

Work claim transaction

Subsection guide · plain-English companion

Plain-English significance: Work claim transaction defines a durable work-control rule rather than an in-memory scheduling convenience. Explicit queue and transition rules preserve causal order and make restart reconstruction deterministic.

Real-life example: A deli takes numbered tickets. A new request is printed immediately, waits behind the active ticket, and moves only through allowed board columns such as queued, preparing, and complete.

The claim transaction updates queued work to running and appends work.started. It performs no context assembly or external I/O.

Model attempt transaction

Subsection guide · plain-English companion

Plain-English significance: Model attempt transaction groups database changes that must become visible together or not at all. A crash between related writes must not leave a message without work, an outcome without an attempt, or completion without an answer.

Real-life example: A hotel booking commits the room reservation and confirmation number as one operation; issuing only one half would mislead either the guest or the hotel.

Before outbound provider I/O:

  1. Model target has already been selected.
  2. Context source eligibility and manifest are finalized.
  3. Persist any canonical context/request artifact bytes before the database references them.
  4. Insert the context manifest and ordered source rows.
  5. Insert model_invocations(state='requesting').
  6. Update work to waiting_on_model with invocation ID.
  7. Append model.invocation_started and work.waiting_on_model.
  8. Commit.
  9. Begin provider I/O.

After provider completion, one transaction updates the invocation with ordered normalized output, usage, stop reason, request IDs, and terminal state; appends the terminal invocation event; and returns work to running unless cancellation or terminal failure wins.

When work returns to running, the same transaction appends work.resumed caused by the terminal invocation event. An exhausted provider failure transitions directly to work.failed instead.

Tool execution transactions

Subsection guide · plain-English companion

Plain-English significance: Tool execution transactions groups database changes that must become visible together or not at all. A crash between related writes must not leave a message without work, an outcome without an attempt, or completion without an answer.

Real-life example: A hotel booking commits the room reservation and confirmation number as one operation; issuing only one half would mislead either the guest or the hotel.

Tool execution uses two pre-side-effect transitions:

  1. Requested transaction: persist the complete model tool call, decoded/validated arguments or structured validation result, tool identity, workspace, requested privilege, and tool.execution_requested. Set work waiting_on_tool.
  2. Dispatch-intent transaction: after authority evaluation and immediately before Workstation invocation, set state dispatching, record effective privilege/deadline/output policy, and append tool.execution_dispatching. Commit.
  3. External execution: invoke Workstation without a database transaction.
  4. Outcome transaction: after canonical artifact bytes are finalized, set the terminal tool outcome, append tool.execution_completed, append work.resumed, and return work to running; or append outcome-unknown/interruption transitions.

A crash after step 2 is intentionally conservative: recovery cannot know whether step 3 started, so the execution becomes outcome_unknown even if the process never actually spawned.

Final-answer transaction

Subsection guide · plain-English companion

Plain-English significance: Final-answer transaction groups database changes that must become visible together or not at all. A crash between related writes must not leave a message without work, an outcome without an attempt, or completion without an answer.

Real-life example: A hotel booking commits the room reservation and confirmation number as one operation; issuing only one half would mislead either the guest or the hotel.

One transaction:

  1. Verifies work is active, not cancel-requested, and owned by the runtime.
  2. Inserts the immutable assistant message.
  3. Appends assistant.message_committed caused by the terminal invocation event.
  4. Transitions work to completed with outcome answered or refused.
  5. Appends work.completed.
  6. Clears current-attempt and runtime ownership fields.
  7. Commits.

The client sees the committed assistant message only after this commit. A process death after commit but before delivery is repaired by cursor replay and must not run the work again.

Cancellation transaction

Subsection guide · plain-English companion

Plain-English significance: Cancellation transaction separates asking an operation to stop from proving that it stopped. External systems and child processes may race with cancellation, so the durable record needs intermediate and terminal facts.

Real-life example: A train controller sends an emergency stop and records 'stop requested'; only a sensor confirmation justifies 'stopped.' If contact is lost, uncertainty remains visible.

Cancellation command state and its journal event commit with the client-command idempotency response. Cleanup completion is a later transaction for active work. Queued cancellation may become terminal in the command transaction because no external action exists.

Required pragmas

Subsection guide · plain-English companion

Plain-English significance: Required pragmas turns SQLite from a file format into an operated durable store. Database correctness depends on connection, synchronization, migration, checkpoint, and integrity policies—not only table definitions.

Real-life example: A records room needs locking rules, fire procedures, inventory checks, and controlled renovations. Merely owning filing cabinets is not an operating system.

Every database connection MUST apply and verify:

PRAGMA journal_mode = WAL;
PRAGMA synchronous = FULL;
PRAGMA foreign_keys = ON;
PRAGMA busy_timeout = 5000;
PRAGMA temp_store = MEMORY;

synchronous=FULL is chosen because control-state durability is more important than marginal write throughput. SQLite documents that WAL mode with FULL synchronizes the WAL on each commit, while NORMAL may lose a committed transaction after power loss. See the SQLite synchronous pragma and WAL documentation.

Do not add performance pragmas without documenting durability effects.

Connection model

Subsection guide · plain-English companion

Plain-English significance: Connection model turns SQLite from a file format into an operated durable store. Database correctness depends on connection, synchronization, migration, checkpoint, and integrity policies—not only table definitions.

Real-life example: A records room needs locking rules, fire procedures, inventory checks, and controlled renovations. Merely owning filing cabinets is not an operating system.

  • SQLx owns a small connection pool; four connections is the V0 default.
  • All write transactions pass through one in-process WriteCoordinator mutex or semaphore.
  • Read-only snapshot/bootstrap transactions may run concurrently.
  • Write transactions use BEGIN IMMEDIATE or equivalent early writer acquisition.
  • No transaction waits for network, process, filesystem capture, or WebSocket delivery.
  • SQLITE_BUSY after busy_timeout is a storage error and metric; an internal transaction may retry only before any external effect.
  • The database file, WAL, and shared-memory files remain on the same local EBS filesystem. Network filesystems are forbidden.

Stage 5 SQLite runtime contract

Subsection guide · plain-English companion

Plain-English significance: This freezes the safe foundation beneath later persistence: one local owner, one reviewed SQLite build, exact durability settings, and a version-zero boundary that cannot accidentally create product data.

Real-life example: Before installing records in a vault, verify the room, lock, fireproofing, access policy, and inventory ledger. Stage 5 proves that shell while deliberately leaving the records shelves empty for Stage 6.

The V0 implementation uses SQLx 0.9 with only sqlite-bundled, runtime-tokio, migrate, and macros; Tokio 1.53 with only macros, rt-multi-thread, sync, and time; and nix 0.31 with only fs. SQLx and its bundled SQLite amalgamation own SQLite access, with no system SQLite dependency. SQLx types MUST remain inside adapters/sqlite; neither application nor the StateStore port may expose a pool, connection, transaction, query, row, SQL, database path, generic CRUD, or callback for arbitrary transaction work.

The database path is exactly <state_root>/db/craxii.sqlite3 and the process-lock path is exactly <state_root>/locks/craxii.lock. state_root MUST preexist; Stage 5 may create only its db/ and locks/ children. Those directories are mode 0700, and new database and lock files are mode 0600. Production provisioning owns state_root, user ownership, and any chown; runtime MUST NOT accept a SQLite URL, URI query parameters, or a production :memory: mode. Missing, non-directory, symlink-leaf, unexpected-type, group/world-accessible, or reliably detectable multi-link state objects fail closed.

The mounted filesystem MUST be locally classified before use. Linux V0 allows ext2/3/4, XFS, Btrfs, tmpfs, and overlayfs. macOS V0 allows APFS and HFS/HFS+. Known remote classes including NFS, SMB/CIFS, 9p, Ceph, and identifiable network-style FUSE mounts are rejected, and unknown classes fail closed. This classification does not prove EBS backing.

In addition to the required pragmas above, every connection MUST apply and verify:

PRAGMA wal_autocheckpoint = 1000;
PRAGMA locking_mode = NORMAL;
PRAGMA trusted_schema = OFF;
PRAGMA recursive_triggers = OFF;
PRAGMA secure_delete = OFF;
PRAGMA mmap_size = 0;
PRAGMA cache_size = -2000;
PRAGMA journal_size_limit = -1;
PRAGMA fullfsync = ON;

fullfsync is semantically verified where supported; Linux MUST NOT be rejected merely because the Apple-specific durability behavior is a no-op when SQLite reports the documented platform-neutral value. Any other unknown or mismatched correctness PRAGMA fails startup. The validated pool maximum is 1..=4, default four; its minimum equals its maximum for eager validation, acquisition timeout is five seconds, and idle timeout and maximum lifetime are disabled. Replacement connections receive the same initialization and verification.

One in-process Tokio WriteCoordinator serializes Craxii writes. Lock order is coordinator, pooled connection, then BEGIN IMMEDIATE. Writes are short bounded SQLite-only transactions with explicit commit/rollback and rollback-on-drop. There is no generic retry loop, nested/savepoint public surface, or escaped transaction handle. Provider/network calls, workstation/process calls, filesystem content reads, artifact rename, client delivery, and unrelated sleeps or waits MUST NOT occur inside a SQLite transaction.

MAX_SUPPORTED_SCHEMA_VERSION remains zero in Stage 5. The embedded SQLx migration set contains zero Craxii migrations and may create only SQLx-owned migration metadata. There is no user_version, Craxii schema-version table, fake migration 0000, or Craxii domain table. Stage 6 owns migration 0001 and the canonical schema. Preflight classifies a database as empty, migrated_uninitialized, newer_schema, corrupt, or inconsistent; only the first two may proceed. A positive applied migration is newer, while failed/malformed/contradictory metadata or any unexpected version-zero user object is inconsistent.

Startup opens and verifies WAL on a dedicated connection, acquires a nonblocking exclusive Unix advisory lock held for the runtime lifetime, eagerly validates the pool, performs compatibility plus quick_check and foreign_key_check before migration mutation, applies the empty forward migration harness, and repeats applicable postflight checks. It never auto-repairs. The returned bootstrap guard owns the pool and lifetime lock, while successful Stage 5 startup remains live_unready until Stage 7 bootstrap and Stage 10 recovery are implemented.

Safe database errors expose only fixed storage, newer-schema, already-owned, corruption, inconsistency, state-conflict, or internal-invariant categories. Raw paths, SQL, bind values, SQLx/SQLite messages, content, and secrets MUST NOT enter Display, Debug, serialized normalized errors, startup diagnostics, source chains, or traces. Sanitized numeric SQLite codes are diagnostic only and MUST NOT be put in SourceStatus::os_errno. A passive checkpoint report is observational, not a backup; shutdown closes the pool and MUST NOT force TRUNCATE.

A successful FULL/WAL commit is treated as durable across process crash and conforming local-storage crash boundaries. This does not promise protection from filesystem or storage failure, EBS volume loss, account or Availability Zone loss, or absent backup.

Key scope

Real-life example: A courier scans one parcel twice; the tracking system recognizes the same parcel ID and updates one shipment instead of inventing a second package.

protocol_version
command_type
conversation_id
client_message_id
normalized ordered content blocks

It does not hash arbitrary JSON serialization, so whitespace and object-key ordering do not affect identity.

Duplicate behavior

Subsection guide · plain-English companion

Plain-English significance: Duplicate behavior makes repeated delivery distinguishable from a genuinely new instruction. Networks lose acknowledgements, so retries are expected. Stable keys prevent the retry path from creating duplicate responsibilities or side effects.

Real-life example: A courier scans one parcel twice; the tracking system recognizes the same parcel ID and updates one shipment instead of inventing a second package.

  • Same device, same key, same command type, same hash: return stored status/body and duplicate=true in the response projection if the protocol includes that convenience field.
  • Same device, same key, different type/hash: 409 idempotency_conflict with no domain writes.
  • Different device, same key: independent scope, though (device_id, client_message_id) still prevents accidental same-device duplication.
  • Concurrent identical requests race on the primary key; the loser reloads and returns the winner's response.

The original response body is stored so a retry after “commit succeeded, HTTP response lost” is unambiguous.

  • a new Unix process group/session;
  • kill_on_drop as defense in depth, not the primary cleanup mechanism;

The server performs:

  1. Authenticate and validate after is nonnegative and not ahead of the current journal head.
  2. Subscribe the connection to the in-process commit notification channel before reading replay.
  3. Read current journal high-water R.
  4. Query and send every client-visible durable event with H < journal_offset <= R in ascending offset order.

ErrorCode is an opaque allowlisted stable-code value, not a public arbitrary string and not a closed exhaustive enum. Construction is crate-private and accepts only approved already-sanitized static or closed diagnostic values; it MUST NOT be built from error.to_string(). How to read the complete flow

The responsibility enters as a durable command. The user supplies one instruction, while the Mac supplies a stable command ID rather than orchestration. Caddy terminates TLS, Axum authenticates and validates the request, and the Command Service makes one atomic acceptance decision. The user message, exactly one work item, its input relationship, journal facts, and the replayable receipt commit together. An acknowledgement therefore means that the responsibility really exists.

Durable state drives execution. The scheduler claims FIFO work from SQLite, so a Tokio task merely executes a responsibility that already survives its death. The explicit agent loop checkpoints its phase, selects a model target, asks the Context Assembler for a causally valid briefing, and records the exact context manifest.

Inference is a replaceable edge. A model-attempt intent exists before Reqwest calls the OpenAI Responses adapter. The provider returns ordered text, tool, refusal, structured, and native items with usage and error evidence. Craxii—not the provider—decides whether that response completes the responsibility or requires another step.

Real machine actions cross a recorded boundary. The Tool Execution Service validates the call, resolves the handler, makes the privilege decision, and commits execution intent before LocalWorkstation touches Ubuntu. File and shell operations have explicit paths, directories, environments, privilege, process containment, timeouts, and output limits. Their observed result—or honest uncertainty—is committed afterward and becomes evidence for the next model invocation.

Completion, connections, and processes remain honest. The assistant message and completed work state commit atomically; streaming drafts never substitute for that fact. WebSocket reconnect uses a durable cursor, while systemd restart and startup recovery reconstruct safe next actions from SQLite. EBS and off-guest snapshots provide the first recovery layer, and stable ports preserve the later route to an external durable core and replaceable RemoteWorkstation.

Full worked example

End-to-end real-life story: “PTG signup is broken. Figure it out. Don’t deploy.”

Situation: the founder is away from their desk and notices that a local development version of PTG no longer completes signup. Craxii's Ubuntu workstation already contains the PTG repository and its test toolchain. The founder opens the native Mac app and writes:

PTG signup is broken. Figure it out. Don’t deploy.

Honest V0 boundary: V0.0.01 can inspect and modify its development workstation, run local tests, and avoid deployment because no production or catastrophic credentials are present. The sentence “Don’t deploy” remains durable user intent and model context, but V0 does not yet claim a mature external authority service that machine-enforces that prohibition. Production credentials are deliberately absent, which makes accidental production deployment unavailable rather than merely discouraged.

Act 1 — the instruction becomes durable responsibility

1

The Mac creates a command identity

The Swift client creates a new client command/idempotency key, for example 01K…PTG. The visible chat bubble may appear optimistically as “sending,” but it is not yet canonical. This is like writing an order number on a request before handing it to a service desk.

2

HTTPS carries a command, not a transient chat event

The app sends an authenticated HTTP message command through Caddy. Caddy owns TLS termination and proxies over loopback to Axum. Tower middleware enforces body limits, timeouts appropriate to command acceptance, tracing correlation, and authentication. The WebSocket is not trusted to be the only copy of the instruction.

3

The Command Service checks whether this is new

The backend looks up the command key within the authenticated device scope. If the founder's Wi‑Fi previously delivered the request but lost the response, the row already exists and the backend returns the same message/work identifiers. If no row exists, this is a genuinely new command.

4

One SQLite transaction accepts the responsibility

SQLx begins an immediate transaction. It inserts the committed user message, creates exactly one queued work_item, links them through work_item_inputs, appends the corresponding journal events with stream sequences and global offsets, and stores the command's durable response. A failure rolls back all of it. Craxii can never observe “the user said it” without also knowing which work item owns it.

5

The client receives an acknowledgement that means something

Only after SQLite commits under WAL/FULL does HTTP return the stable message ID, work-item ID, and command status. The Mac replaces its “sending” state with a committed projection. If the response is lost, resubmitting the same key finds the same work rather than opening a second investigation.

Act 2 — the scheduler and agent loop begin the job

6

The durable scheduler claims the first eligible ticket

The scheduler queries SQLite, sees no active item in this conversation, and atomically moves this work item from queued to running with the current runtime_instance_id. A Tokio task starts only after that commit. If the task disappears, the job ticket still exists and startup recovery can see who claimed it.

7

The agent loop checkpoints its phase

The explicit Craxii-owned loop records that the work is preparing a model step. This code—not OpenAI, not Axum, not a hidden agent framework—decides the next action and eventual terminal condition. Correlation and causation IDs connect every later model and tool attempt to this responsibility.

8

Model Selection picks a target before prompt rendering

V0 has one configured real OpenAI target, but the selection boundary still evaluates required capabilities such as tool calling and configured context size. It records the target and the simple selection reason, such as “only configured target satisfying tool-use capability.” No sophisticated router is invented.

9

The Context Assembler creates an exact briefing

The assembler reads durable conversation history only up to this work item's causal frontier. It includes the founder's PTG instruction and eligible prior committed messages; it cannot include later queued user input. It renders for the selected model, measures bytes/tokens, and commits a context_manifest plus ordered context_manifest_sources. If full history does not fit, V0 fails explicitly instead of silently dropping the “Don’t deploy” instruction.

10

A provider attempt has intent before network dispatch

A model_invocation attempt records provider, model target, attempt number, manifest, selection reason, and dispatch intent. Then the OpenAI Responses adapter translates Craxii's canonical request into provider wire types and sends it with Reqwest using server-side credentials. The request is stateless from Craxii's perspective and uses store=false; OpenAI conversation state is not the system of record.

Act 3 — inference requests real workstation evidence

11

The response preserves order and native evidence

Suppose the model emits a short reasoning-facing text item followed by two tool calls: read the repository's signup handler and run the focused signup test. The adapter returns ordered output items, usage, stop reason, provider request ID, latency, and native continuation metadata. It does not flatten the response into only “text or tools.” The agent loop decides that tool requests mean the responsibility is not terminal.

12

The Tool Execution Service validates the first request

For read_file, the service confirms that this work item is active, the tool call identity has not already been consumed, arguments match the registered schema, and the requested logical path can be resolved. The Tool Registry supplies the definition and handler; it does not write database state or schedule the loop.

13

Intent is committed before reading the machine

The service inserts a tool_execution attempt and a journal intent event before calling the handler. A read is relatively safe to retry, but Craxii applies the same evidence discipline so every model-visible observation has provenance. The stable tool execution ID follows the operation through the Workstation port.

14

LocalWorkstation reads the actual PTG file

The model-facing handler asks LocalWorkstation.read_file for a low-level file operation. LocalWorkstation resolves the logical workspace under /srv/craxii/workspaces, enforces allowed size and path behavior, reads bytes, and reports encoding and truncation honestly. If the target is binary, it does not pretend those bytes are source text.

15

The observed read result becomes durable evidence

The service commits the bounded structured result after the read. If output is too large, full bytes are atomically written to the content-addressed artifact store, hashed, and referenced by metadata while a bounded excerpt goes to the model. The journal tells future readers exactly which tool attempt observed which file content.

16

The shell test runs in a controlled real environment

For run_shell, the model requests something like cargo test signup_flow -- --nocapture with the PTG workspace as explicit cwd. The handler records user-level privilege, constructs a sanitized allowlisted environment, invokes non-interactive Bash, and gives the execution a process group/cgroup identity. Stdout and stderr are captured separately and bounded. A timeout triggers TERM, a grace period, then KILL for the owned process tree.

17

A failing test is evidence, not infrastructure failure

The test exits with code 101 and shows that a newly required marketing_consent field is absent in the local request fixture. Nonzero exit is a completed command result, not a Tool Execution Service failure. Craxii persists exit code, stderr/stdout, duration, signal state, truncation flags, and the exact command/cwd/privilege context.

Act 4 — Craxii reasons again, changes its workstation, and verifies

18

A second context manifest includes the new evidence

The loop selects the model target again and assembles a fresh briefing. Its manifest now references the original instruction, the first model response, both tool intents and results, and any bounded artifact excerpts. The previous provider response ID may be preserved as native continuation data, but durable Craxii history—not the provider's server-side thread—remains authoritative.

19

The model proposes a local development fix

The model asks run_shell to patch the fixture or source using a deterministic shell operation, then rerun the focused test and perhaps the relevant test suite. In V0, high-level edit/install/test actions can be implemented through the generic shell tool rather than expanding Workstation into a giant method catalogue. Each requested command still receives a separate stable tool execution record.

20

Privilege remains explicit even when autonomy is broad

The change needs no root privileges, so it runs as the craxii Unix user. If a missing local toolchain required an administrative package installation, the request would explicitly select administrative mode through the privileged execution path. The backend itself never runs permanently as root. Because Docker/root access weakens internal isolation, the architecture does not misrepresent Unix users as a strong security boundary.

21

Verification closes the evidence loop

The focused test passes, then the broader local signup suite passes. The tool outcomes, command output, timings, and modified workspace state are durable on EBS. Craxii has not deployed anything and has no production credential capable of doing so. The model receives the verification evidence in another exact context manifest and produces an ordered final text response.

Act 5 — the final answer becomes committed conversation

22

Draft text may stream, but it is not history yet

As provider text arrives, the WebSocket may carry ephemeral draft chunks tagged with invocation and draft identities. The Mac can render them as temporary progress. They have no durable replay cursor and cannot become a conversation message merely because the UI displayed them.

23

One final-answer transaction closes the responsibility

The backend inserts the committed assistant message, marks the work item completed, appends completion journal events, and makes the durable event available at the next global replay offset in one transaction. The answer says what failed, what local change was made, which tests passed, that nothing was deployed, and where relevant evidence lives. If this commit fails, Craxii does not tell the client that the work completed.

24

The native client reconciles to committed truth

Event Delivery sends the committed message at cursor N. The Mac replaces any matching draft with the authoritative message ID and advances its applied cursor. If the WebSocket dropped between commit and delivery, reconnect starts after the previous cursor and replays cursor N. The answer appears once even though transport may have attempted delivery more than once.

Act 6 — a second message arrives while the first is running

25

The founder adds another responsibility

While the first test is still running, the founder writes, “Also tell me how many signup tests we have.” V0 does not steer the active loop. The backend accepts this as a new committed message with exactly one new queued work item and immediately acknowledges it.

26

Causal isolation prevents future leakage

The active PTG-fix context manifest cannot include the later test-count message. The new work waits FIFO. After the first work item completes, the scheduler claims the second; its context may include the earlier completed investigation because that history is now causally prior. This produces simple, predictable semantics without a multi-agent system.

Act 7 — the backend is killed and the relationship continues

27

systemd restarts a process, not an identity

An operator kills craxii-server for the benchmark. systemd's service cgroup kills ordinary descendants and starts a new Rust process. The new boot writes a new runtime_instance_id. Craxii's principal ID, messages, work items, tool evidence, and journal remain on encrypted EBS; none are derived from the old PID.

28

Startup recovery runs before readiness

The server opens SQLite with required pragmas, applies compatible migrations, checks integrity, registers tools/providers, marks the previous runtime instance ended abnormally, and scans incomplete work and attempts. It classifies each using durable phase and dispatch evidence before the scheduler is allowed to claim anything.

29

A follow-up is answered from reconstructed history

After readiness, the founder asks, “What exactly did you change in signup?” This is another message and work item. Its naive full-history context is rendered from SQLite, including the committed PTG answer and tool evidence. Craxii answers even though the original model call, WebSocket, Tokio task, and PID are gone. That is the V0 continuity proof.

Act 8 — the dangerous crash window stays honest

30

A non-idempotent command is dispatched

In the failure benchmark, imagine an administrative shell command that starts or changes a local service. The Tool Execution Service commits dispatch intent, LocalWorkstation starts it, and then the backend is killed before the observed result transaction commits. The real machine may have changed.

31

Recovery refuses to guess

On restart, the execution record says dispatch began but has no terminal observation. Because the operation is not proven idempotent, Craxii does not automatically run it again and does not invent a failure. It marks the tool execution outcome_unknown (and the work item interrupted/failed according to the defined policy), preserves the command and evidence, and reports the uncertainty.

The user gets a trustworthy blocker

The visible result is less magical but more valuable: “The service-change command may have run before I restarted. I cannot safely repeat it without inspecting the machine.” A later responsibility can inspect actual service state. This is what “persistent coworker” means under failure: Craxii preserves what it knows, what it observed, and what it cannot honestly claim.

What this story proves—and what it deliberately does not

Proved by V0.0.01

  • One continuous user-facing conversation can produce durable FIFO work items.
  • The model can request real Linux tools through Craxii-owned control flow.
  • Intent and observed outcome surround external calls.
  • Context comes from Craxii's durable history, not provider conversation state.
  • Client and backend reconnect without duplicate work or missing committed events.
  • Restart reconstructs history and classifies incomplete attempts honestly.

Not claimed by V0.0.01

  • Machine-enforced “do not deploy” policy beyond absence of production authority.
  • Survival of total EBS and snapshot destruction.
  • Durable core independent of the workstation VM.
  • Semantic long-term memory, compaction, or vector retrieval.
  • Safe arbitrary daemon/session resumption.
  • Parallel responsibilities, steering, or multi-agent orchestration.

The architectural significance: the impressive part is not that an LLM can suggest a signup fix. The product proof is that one durable Craxii identity accepts the responsibility exactly once, assembles evidence honestly, uses a replaceable inference engine, operates its real computer, records side effects, survives loss of transient processes and connections, and returns with a reconstructable answer—or a truthful statement of uncertainty.
